# 去哪儿都行 · 多智能体旅行搭子

打开网页说一句话（可以带图），它先读懂你想要什么，推荐三个地方，你说去哪个，
然后排出带图、带亮点、带避坑的行程；玩到一半累了、下雨了、太赶了，它能只改那一天。

**纯对话**，没有要点的卡片；每条安排都能就地「换一个」。

```
你：我们两个五一去大理玩三天，她喜欢拍照，我怕人多

它：她想要的是一次能拍出好看照片、但避开五一人群、节奏安静松弛的大理三天旅行。
    像这几个：大理、婺源、青岛。要不先按大理排一版？

你：就这个吧
它：好，大理，3 天。[第 1 天 · 上午 沙溪古镇 …]

你：第 1 天下雨了
它：第 1 天换成室内了：2 个从别的天挪过来，那边的户外挪到晴天去。
```

## 这个项目是怎么来的

两个版本合成一个：

| 从这里来 | 拿到了什么 |
|---|---|
| 旧版 `trip_crew_agent` | **`crewai_bootstrap`**（Windows 上不加会卡死）、工具失败要显式标注的习惯、单测意识 |
| 新写的 `travel/` | 三层隐性偏好、确定性排程内核、纯对话状态机、攻略卡片、配图 |

旧版的 Streamlit 界面没有合并进来——它和"纯对话"是两种交互，留两套只会让演示时分不清哪个是真的。
旧代码还在 git 历史里（`git show b4bb516:app/streamlit_mvp.py`）。

## 架构

```
浏览器（对话 + 攻略卡）
      │  /api/session /message /swap /adjust /photo
      ▼
会话状态机 session.py     0 开场 → 1 选地方 → 2 行程 → 3 调整
      │
      ▼
Agent 层（CrewAI 三个）
   Profiler  文字+图片 → 三层画像
   Matcher   候选 → 3 个目的地 + 理由
   Planner   草稿 → 人话 + 一个问题
      │  只调函数，不算数
      ▼
计算层（纯 Python，可单测）
   engine.py  打分 / 选目的地 / 背包排程 / 换点
   adjust.py  下雨 · 累了 · 太赶
   vibe.py    点位气质推导
      │
      ▼
数据层                       外部数据
   6 目的地 × 9 点位          高德：天气 / 路线 / 地点 / 实景图
   SQLite 会话                维基共享资源（配图备选）
                              Tavily（联网搜索，可选）
```

一条约定：**Agent 负责读懂人和说人话，代码负责算和兜底。**

## 三个 Agent

| Agent | 输入 | 输出 | 什么时候跑 |
|---|---|---|---|
| **Profiler** | 每人的文字 + 图片线索 | 每人一份 `Profile`（含三层） | 收到第一句话 |
| **Matcher** | 画像 + 候选目的地 | 2~3 张卡 + 一句理由 | 同一轮 |
| **Planner** | 已排好的草稿 | 具体到能照着走的攻略 + 一个真问题 | 后台补（`/api/polish`） |

Planner 只改文字，**不许改点位**（guardrail 会拦：poi_id 不在草稿里就打回重试）。
所以"选哪几个点"永远是确定的，模型只负责说清为什么。

没有 key 时三个 Agent 全部由规则替代，接口不变。

## 隐性偏好分三层

| 层 | 存哪 | 怎么用 |
|---|---|---|
| **审美** | `Taste` 5 维，[-1,1] | 和景点/目的地的同一组维度算相似度 |
| **情绪** | `Emotion` 6 种需求，[0,1] | 点位气质能不能满足；`control` 决定一天排几个 |
| **社交** | `Social` 3 项 | 独处/结伴、看/参与、人流容忍度 |

图片和文字都往这三层上落，冲突时两边都留在 `evidence` 里，不擅自选一个。

图片不是拿去"以图搜图"，而是先转成这 14 个数，再和点位属性比——
所以能解释"为什么推荐这个"，也能解释"哪一维不匹配"。

点位气质（`vibe.py`）从品类和标签推导，不手写：审美必须人工标（要和用户对齐），
情绪/社交可以推（规则可解释）。

## 出来的是攻略，不是行程单

```
[图] 上午
     沙溪古镇
     安静、老房子，对上你想的「安静」        ← 为什么是它
     老房子和巷子，慢慢走才有意思            ← 一句话亮点
     半天起步，带水，人均 ¥50，营业/预约未核实   ← 点开才显示
     [换一个]   150 分钟 · ¥50
```

- **图**：高德点位实景图 → 维基共享资源 → 当场画的占位图。永不出现破图。
- **换一个**：只替换这一个点，其他天其他条不动，且受当天时长预算约束。
- **折叠**：点天标题收起整天，点条目展开避坑。
- **汇总**：顶部给天数、总小时数、人均花费。

|---|---|
| 下雨 | 户外换室内；本城没空闲室内就从别的天借，把那天的户外挪到晴天 |
| 累了 | 去掉当天最费体力的那个 |
| 太赶 | 去掉当天最不值的那个 |

天气走高德 `weather/weatherInfo`。没配 key 时写"天气没拿到，出发前自己看一眼"，不编。

## 三个坑（这个环境里踩出来的）

**1. `import crewai` 会卡死**
不是慢，是卡住。模块级 tracing 构造 → `get_writable_config_path()` 用
`tempfile.mkstemp` 试写候选目录，落到受限路径上就会无限期挂起。
`travel/crewai_bootstrap.py` 把配置路径指到临时目录，**必须在 import crewai 之前调用**。
实测从"卡死"变成 2.7 秒。

**2. `response_format={"type":"json_object"}` 不能挂在 LLM 上**
DeepSeek 要求 prompt 里出现 "json" 字样，而 CrewAI 内部的工具选择调用不含，
会 400 并触发重试风暴。正确做法：**不设 response_format**，靠 task 里写清楚 JSON，
再用 guardrail 兜。

**3. `output_pydantic` 在 DeepSeek 上用不了**
CrewAI 会走 `chat.completions.parse`（json_schema），DeepSeek 直接返回
`This response_format type is unavailable now`。
改成不设 `output_pydantic`，自己解析 raw + guardrail 校验，能跑。

顺带：guardrail 函数**不要写返回类型注解**。本文件有 `from __future__ import annotations`，
注解会变成字符串，CrewAI 校验 `Tuple[bool, Any]` 时判定失败。

## 实测

| 项 | 耗时 | 说明 |
|---|---|---|
| 说话 → 画像 + 3 个候选 | **5.8s** | 一次调用，顺带砍掉了原来单独跑推荐官（省 5s） |
| 选地方 → 行程出现 | **0.1s** | 排程是纯代码，模型不再挡在路上 |
| 攻略文案补齐 | 7s（后台） | 你在读行程的时候它才写 |
| 单测 | 0.06s | 12 个 |

真实产出（沙溪古镇那条）：

> **highlight**：七点半到寺登街，从兴教寺那侧进，拍空街和戏台，逆光拍木门。
> **tip**：古镇免费，兴教寺门票约 20 元（未核实）；大理出发车程约 2.5 小时，
> 建议 7 点前出城；店铺 10 点后才开，早到吃不到早饭。
> **question**：自驾还是包车？这决定沙溪能不能 8:30 前到。

对比一下模板时代的那句"老房子和巷子，慢慢走才有意思"——差别不在模型，在**有没有让它写具体的**。

## 为什么快，以及为什么之前慢

之前一次规划要等 ~25 秒，三个原因：

1. **推荐官单独一次调用** —— 只为写三句理由，+5s。砍掉，用引擎的理由。
2. **让模型复述整份行程 JSON** —— 输出两千多 token，被截断后 guardrail 反复重试，
   表现出来就是"卡十几秒然后什么都没变"。改成只回文字（`PlanPatch`），输出砍半。
3. **模型挡在排程前面** —— 排程本来是纯代码、毫秒级，却要等模型写完才返回。
   现在先秒回行程，文案走后台 `/api/polish` 补上。

现在的体感：**说一句话 5.8 秒出画像和候选，点选后 0.1 秒出行程**，攻略在你读的时候悄悄变好。

## 数据库只是缓存，不是真相

一开始我把点位库当成了唯一来源，结果是：**只能去这 8 个地方**。
你发一张罗弗敦的照片，它照样推大理——因为库里只有大理。

现在两条路：

| 情况 | 用谁 | 可信度 |
|---|---|---|
| 库里有（8 个目的地 / 68 个点） | 人工标过审美的点位 | 高，但仍是抽样 |
| 库里没有（任何城市） | 模型按记忆现场写（`run_draft_pois`） | 低，**全部标"未核实"** |

实测：发一张挪威雷讷的雪景 → 它认出来了，说"这种地方我库里没有点位，硬推大理就是糊弄你"，
给两条路。选"真去"，它排出：

> 第1天 Olenilsøya 小岛步道 / Reine 码头蓝调时刻
> 第2天 Djupfjord 桥 / Lofoten 鳕鱼博物馆
> 第3天 Reinebringen 登山步道 / Sakrisøy 渔村

这些是模型的知识，不是库里的。风险也写明白了：**没核实，当草稿用**。
以后接上高德（境内）和联网搜索（境外），这一层的可信度才真正提上来。

另外：**用户已经说了城市，就别再让他从三个里挑**。现在说"五一去大理"会直接出行程。
