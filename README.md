# 去哪儿都行 · 多智能体旅行规划

**把"我想找个安静的地方待几天"变成一份能照着走的行程。**


它做的是：读懂人 → 找出矛盾 → 排一条真能走的路 → 你说改哪就改哪。

```
你：五一两个人去大理三天，她喜欢拍照，我怕人多

它：我把这句话拆成两个人了：她是要出片的，你是怕挤的。
    这俩在大理五一确实会打架——好机位基本都在人多的地方。
    但有个解法：不靠选地方躲人，靠选时间躲人。早上七到九点出去拍，
    光最好人也最少，你俩的诉求在同一个时段里能同时满足；中午人最多的时候
    回客栈待着，她修图你睡觉。

    她拍照是愿意为了好光线早起、在一个点待很久那种，还是边走边随手拍？

你：就这个吧

它：【第 1 天】8:20 出门，先在古城吃碗饵丝，10 到 15 块，人民路下段那几个早市摊最稳。
    8:40 上车，大丽路一路向北，40 分钟到海舌停车场。9:10 进园，别在入口那片
    开阔地就停住拍，沿主路走到半岛尽头的情人树，15 分钟，两边都是水，风大，帽子拿住。

你：第 1 天下雨了

它：第 1 天换成室内了：1 个直接换掉，1 个从别的天挪过来，那边的户外挪到晴天去。
```

## 一、偏好：从一张图里读出"缺什么"

用户发的图不是"想去哪"，是"想要什么感觉"。传统做法是拿图去搜图，
这里做的是把图拆成三层可计算的量：

| 层 | 存成什么 | 用来干什么 |
|---|---|---|
| **审美** | 5 维，[-1,1]：安静↔热闹、自然↔城市、极简↔繁复、温暖↔冷冽、经典↔新潮 | 和点位的同一组维度算相似度 |
| **情绪** | 6 维，[0,1]：恢复、新鲜、掌控、归属、审美、成就 | 判断"这天该松还是该密" |
| **社交** | 3 维：独处↔结伴、旁观↔参与、能忍多少人 | 决定点位挑选和时段 |

图片先过一次视觉模型，产出**地名猜测 + 场景维度（地理/天气/光线/人物/活动/花费/人流）+ far 标记**，
再喂给推理 Agent。far 是"这地方和常规国内游差多远"——标出来，才不会拿大理去糊弄一张北欧照片。

推理 Agent 的五步，是这份 prompt 里真正值钱的部分：

1. **先分清谁说的**——一句话里常混着两个人的诉求，归因到人，不许平均摊
2. **五层读图**——空间（开阔→要自由）、人物（无人→内向充电）、色温（冷→冷静）、秩序（粗粝→释放）、时间（黄昏→感性）
3. **读文字信号**——否定比正面要求更硬；"随便"是决策疲劳，不是没要求
4. **落成数字**——任何超过 ±0.7 的极端值必须在 evidence 里写依据
5. **只在置信度低于 0.6 时才问**——宁可不问，也不问"你想住哪"

## 二、冲突：Shapley 值 + 让步账本

多人出行必然冲突，但"取平均"会把两个人的诉求一起抹平。这里的做法：

```
候选方案集 P（同一批点位，出 3~4 个取舍不同的版本）
        ↓  U[i][j]：每个人在每个方案上的满意度
v(S) = max_{p∈P} Σ_{i∈S} u_i(p)        ← 关键：联盟只能共享同一个方案
        ↓
φ_i = 精确 Shapley（n≤5，2^n 枚举，毫秒级）
        ↓
选方案：最大化 Π u_i（比例公平），不是最大化总和
        ↓
让步账本：Δ_i = 独自最优 − 实际拿到
```

**为什么 v(S) 必须写成"共享方案"**：如果写成每人各取各的最优，
`φ_i` 就退化成"这个人自己最想要的东西有多想要"，跟联盟里还有谁完全无关——算了个寂寞。
写成共享方案之后，加一个人会改变"大家一起选哪个"，边际贡献才依赖联盟构成。

**φ 高不等于话语权大，恰恰相反**：φ 高是好带（有他不多没他不少），
φ 低才是被牺牲的那个。所以补偿用 Δ 定价，不用 φ 加权。

界面上是一本账：

```
这本账
第 1 位   让了 0.03    独自最好 0.67 → 实际 0.63
第 2 位   让了 0.02    独自最好 0.69 → 实际 0.67
```

**一个诚实的发现**：三天两夜的行程装得下两个人的偏好时，账本全是 `0.00`。
不是算法失效，是**真的没冲突**——冲突来自稀缺，时间位够的时候公平分配是个伪问题。
这条比代码更值得记住：知道机制该在什么条件下用，比到处挂一个 Shapley 标签有用。

## 架构

```
浏览器（纯对话 + 攻略卡 + 账本）
      │  /api/stream (SSE) · /api/polish · /api/swap · /api/adjust · /api/photo
      ▼
会话状态机 session.py      0 开场 → 1 候选 → 2 行程 → 3 调整
      │
      ├─ 并行 ─┬─ 读人   vision.py → agents.run_profiler（五层 + 归因 + 矛盾）
      │        └─ 写点位 agents.run_draft_pois_auto（认城市 + 8~12 个点位）
      ▼
计算层（纯 Python，可单测，同输入同输出）
      engine.py  打分 / 背包排程 / 候选方案集 / 时间轴 / 换点
      game.py    Shapley / Nash / 让步账本 / 核心阻塞
      adjust.py  下雨 · 累了 · 太赶
      vibe.py    点位气质推导
      ▼
外部数据（拿不到就返回 None，绝不编）
      live.py    高德：天气 / 路线 / 地点 / 点位详情
      guides.py  联网攻略 → 抽事实（带来源编号）
      resolve.py 冲突：按最新取，旧说法降级保留
      photos.py  配图：高德实景 → 维基 → 当场画的占位图
```

一条约定：**Agent 负责读懂人和说人话，代码负责算和兜底。**

## 已知限制

- **点位和时长是模型按记忆写的，没核实。** 每条标"未核实"，行程末尾固定一句"出发前自己再核一遍"
- 接上高德后，评分/营业时间/地址是查出来的；接搜索后，门票和避坑从攻略里抽——**冲突单列、按最新取**，不选边
- 效用函数底太高（大多落在 0.6 附近），所以即使有冲突，账面数字也偏小；要让"让了多少"更刺眼，得把权重调开
- 单人出行其实用不上多智能体；这套设计的价值在多人冲突
- 通勤时间按同城 25 分钟估，点位没有坐标

## 踩过的坑

| 现象 | 原因 | 解法 |
|---|---|---|
| `import crewai` 卡死几分钟 | 模块级 tracing 构造 → `get_writable_config_path()` 用 `mkstemp` 试写受限目录 | 导入前把配置路径指到临时目录（`crewai_bootstrap.py`），2.7s |
| 模型调用 400 "Prompt must contain the word 'json'" | `response_format=json_object` 挂在 LLM 上，CrewAI 内部调用不含 json | 不设 `response_format`，靠 prompt 给形状 + guardrail 兜 |
| 400 "This response_format type is unavailable" | `output_pydantic` 会走 `chat.completions.parse`（json_schema），DeepSeek 不支持 | 不设 `output_pydantic`，自己解析 raw |
| guardrail 报 "must be Tuple[bool, Any]" | 文件有 `from __future__ import annotations`，注解变成字符串 | guardrail 函数不写返回注解 |
| 卡 20 秒然后什么都没变 | 让模型复述整份行程 JSON，超 `max_tokens` 被截断 → guardrail 重试两次 | 只让它回文字（`PlanPatch`），并把上限提到 8000 |


## 设计上否掉的东西

- **Agent 辩论**：成本高、结论不可复现、无法评测。旅行规划不需要"吵出共识"，需要可度量的分配
- **让模型排程**：同一输入两次结果不同、不能校验时长、说不出为什么选 A。排程是组合优化，交给代码
- **一次生成全部**：用户等不起，也没法改。改成"结构先回、文案后台补、改动只动一处"
- **"AI 攻略总结成一段话"**：会把互相矛盾的攻略抹平，输出一段读起来很确定、其实谁也不知道的文字
